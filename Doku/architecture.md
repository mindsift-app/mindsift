# Architecture

## Overview

```
Browser (React SPA, PWA manifest)
   │  REST /api/v1/*           Authorization: Bearer <JWT | mindsift_sec_…>
   │  WebSocket /api/v1/ws     Fallback: SSE /api/v1/events, then Long-Polling /api/v1/events/poll
   ▼
Go server (chi)  ── internal/api   Handlers, middleware, alarm ticker
   │                internal/ws    Hub (rooms, user channels, SSE, long polling)
   │                internal/auth  JWT, bcrypt, API key hash
   ▼                internal/config
SQLite (modernc.org/sqlite, WAL)  ── internal/storage
```

The frontend is embedded into the binary via `go:embed` ([cmd/server/main.go](../cmd/server/main.go)). Unrecognized paths return `index.html` (SPA routing), except paths that cannot be a page of the app: a file extension in the last segment, a segment starting with a dot (`/.env`, `/.git/config`), anything under `/assets/`, `/metrics` (unless `METRICS_TOKEN` switches it on, see below) and `/debug/`, and the build's folders; these answer `404` (`notAppPage` in [server.go](../internal/api/server.go)), so scanners do not take them for hits. `HEAD` is answered like `GET`; `index.html`, `sw.js`, and `manifest.json` are served with `no-store`. Links to items (`?note=`, `?task=`, `?list=`, as the MCP server hands them out) open in the installed app where the platform allows it: the manifest has `handle_links: "preferred"` and `launch_handler.client_mode: ["focus-existing", "auto"]`, so an open app window comes to the front and receives the link via `window.launchQueue` (`App.tsx`) without reloading. Whether a link is captured is up to the browser and system: Chrome and Edge on the desktop ask once (or follow the app's "open supported links" setting), on Android it depends on the app's "Open supported links" setting, and apps that open links in their own in-app browser never hand them over.

## Design Decisions

MindSift builds several things itself that other projects take from a library, and leaves out things that are standard elsewhere. The reasons, each with its price:

- **One process, one SQLite file.** MindSift is for one person, a family or a team on a small server. One file is backed up by copying it, there is nothing to run besides the container, and in the load test one core carried about 200 people working at the same moment (README, "Performance"). The price: no cluster and no load balancing, since the realtime hub, the login guard and the stream tickets live in the memory of that one process; and no PostgreSQL.
- **Own note sync instead of a CRDT library (Yjs, Automerge).** Two reasons. The server has to understand a note rather than store an opaque binary: it checks rights on every change, feeds search, hashtags and backlinks and writes Markdown, and there is no mature Yjs for Go. And sync has to work where WebSockets do not: Yjs was tried and did not run reliably behind a company proxy that blocks or cuts WebSocket connections. So every change is an ordinary HTTP request against an operations log on the server, with a version and a lease per bullet; WebSocket, SSE and long polling only wake the clients up, and changes made offline wait in the browser. The price: two people cannot type in the same bullet at once; the second one sees who is editing, or gets a conflict copy. Details and the tests behind it: [modules/collaboration.md](modules/collaboration.md).
- **Own OAuth server.** claude.ai and ChatGPT only connect to an MCP server through OAuth issued for that server itself: discovery (RFC 9728/8414), dynamic client registration and the code flow with PKCE. That is a small authorization server for exactly one resource ([oauth.go](../internal/api/oauth.go)), which an OIDC client library does not provide. Signing in to MindSift through an identity provider is the other direction: MindSift is the client there ([oidc.go](../internal/api/oidc.go), see [Authentication](#authentication)), with `github.com/coreos/go-oidc/v3` and `golang.org/x/oauth2`.
- **Own MCP server.** MCP over HTTP is JSON-RPC in a POST request with four methods (`initialize`, `ping`, `tools/list`, `tools/call`); the work is in the tools ([mcp.go](../internal/api/mcp.go)). A library would add more dependency than it saves code.
- **Own drawing layout and Mermaid reader.** AI agents hand in flowcharts and mind maps as Mermaid, and the server turns them into drawings that stay editable: shapes, and elbow arrows that dock to them. No Go library lays a graph out into that model, so `internal/drawing` reads the two diagram types and places them itself.
- **Two chunks, all loaded at install.** The app is meant to be installed and to work offline after its first start: the shopping list without reception, synchronised later. The entry chunk holds the shell and everything before signing in (login, registration, setup, password reset, OAuth consent, less than 180 kB compressed; the texts of every language are chunks of their own); the app's views are one more chunk ([app/mainViews.ts](../frontend/src/app/mainViews.ts), less than 250 kB compressed), loaded in one place ([app/useMainViews.ts](../frontend/src/app/useMainViews.ts)) as soon as a session exists, with a stored session right at startup. Public note pages use it too (they render with the outliner). The views are not split further; only what a session may never need loads on demand: language files, the help of each language, code grammars, the emoji picker (only types may be imported statically from `emoji-picker-react`, a value would pull the library back into the app chunk), the drawing editor (`DrawingBlock` loads `DrawingEditor` with `React.lazy`; the preview stays in the app chunk) and Motion's drag and animation features for the triage cards (`LazyMotion` with `m.div` in `TriageDeck`; its `strict` flag makes a `motion.div` there an error, as that would pull all of Motion back in). `ci/local-checks.sh` checks the compressed size of both chunks against fixed bounds. The service worker loads every file of the build when it installs (the build writes the list into `sw.js`), so "opened once" still means "all there offline", on-demand chunks included.
- **Few dependencies.** Eleven direct Go modules (router, CORS, JWT, WebSocket, web push, bcrypt, the HTML tokenizer of `x/net` for link previews, SQLite, and for signing in `go-oidc` with `x/oauth2` for OpenID Connect and `go-webauthn` for passkeys) and a handful of npm packages at runtime (React, i18next, Motion, Prism, the icons, an emoji picker). Markdown, rate limiting, the server's translations, dropdowns and the calendar are own code: less that breaks or needs a security update overnight, more that has to be covered by MindSift's own tests.
- **Grown rather than designed: the session.** A sign-in is a signed JWT, a row in `sessions` and `users.token_version` (see [Authentication](#authentication)). Since every request looks up the session anyway, the signature no longer saves anything; a random session ID would do the same with less. It works and is tested, so it stays until sign-in is touched for another reason.

## Startup and Runtime

1. `config.Load()` reads the environment (see below).
2. `storage.NewStore()` opens SQLite (`busy_timeout`, WAL, max 8 connections) and executes `migrate()`; the server then logs the built-in SQLite version (`Database opened sqlite=…`).
3. SMTP values from the environment are imported into `system_settings` if none are present.
4. When the demo flag is set, `EnsureDemoAccounts` creates the `admin/admin` and `user/user` accounts; on first start the admin gets the sample data, all of it shared with `user` for editing (top-level folders as shared folders, the other notes, task lists and lists one by one).
5. `api.NewServer` starts the **alarm ticker** (every minute), the **note log compaction** (on startup, then every 6 hours), the **retention cleanup** (2 minutes after startup, then hourly; disabled in demo mode), and builds the router. Server timeouts: read 15 s, write 30 s, idle 60 s. Handlers that need longer extend them for their own request (`internal/api/bodylimit.go`): uploads and downloads of whole files get 30 minutes, requests on which the server itself works for a while or waits for a mail server or push service (restoring a backup, writing all backups, deleting an account, test mail, test alarm, invite mail, test push) get 5 minutes; streams and long polling have no write timeout. The app waits 12 s for an ordinary answer and 5 minutes for the second group (`REQUEST_TIMEOUT` in `frontend/src/lib/api/client.ts`); file transfers have no timeout in the app. Graceful shutdown on termination.

## Monitoring

`GET /api/v1/health` only says that the server answers (the container's health check, every 30 s); `?db=1` also runs `SELECT 1` with a 2-second limit and answers `503` when the database does not. `/metrics` exists only with `METRICS_TOKEN` (at least 16 characters, also `METRICS_TOKEN_FILE`), checked in constant time as bearer token; without it the path is an unknown one (`404`), as scanners expect. The metrics are written by a small exporter of our own ([internal/metrics](../internal/metrics/metrics.go), Prometheus text format 0.0.4) instead of the official client library and its dozen modules. Counted as things happen ([api/metrics.go](../internal/api/metrics.go)): API requests and their duration by method, chi's route pattern (`/api/v1/documents/{id}`, never the id) and status (in `apiLoggingMiddleware`), mails by result (`sendEmailHTMLWith`), backup runs by result and the time of the last good one (`runBackups`). Read when Prometheus asks: build version, start time, accounts and accounts with a session used in the last 24 hours, the database pool (`sql.DBStats`) and the size of the database and its write-ahead log, goroutines, heap and GC cycles. No label carries a person, an address or an id.

## Authentication

- **Login** with email or username (`login`). New accounts get their username from the display name ("Sandro Dach" → `sandro.dach`, a number appended when taken; migration 20 did the same for existing accounts), changeable in the profile and by admins ([storage/username.go](../internal/storage/username.go)). A login typed like a display name is read as the username; the email prefix still works. Passwords: bcrypt (`DefaultCost`) over the base64 SHA-256 of the password, stored as `sha256-bcrypt:<bcrypt hash>`, so passwords count past bcrypt's 72 bytes (up to 1024 characters, `auth.MaxPasswordLength`). Plain bcrypt hashes of earlier versions still sign in and are replaced by the new form at the next successful login (`auth.PasswordNeedsRehash`, `SetPasswordHash`, no session ends). Public link passwords use the same functions.
- **Two-factor sign-in** ([api/mfa.go](../internal/api/mfa.go), [storage/mfa.go](../internal/storage/mfa.go), TOTP in [auth/totp.go](../internal/auth/totp.go)): per account an authenticator app (RFC 6238: HMAC-SHA1, 6 digits, 30 s, one step of tolerance either way, own code tested with the RFC vectors). The secret is sealed with `SECRETS_KEY` like hidden values (additional data `totp:<user id>`); the last used step is stored, so a code works once. Setting it up needs the password, then the first code switches it on and returns ten recovery codes once (only `SHA-256(user id:code)` is kept, each usable once). With the app on, `POST /auth/login` checks the password as before and answers `{mfaRequired, mfaToken, methods}`; the mfaToken lives 5 minutes in memory, bound to the account and its `token_version`, takes at most 5 wrong codes and is no session. `POST /auth/login/mfa` with the app's code or a recovery code starts the session. Wrong codes count in the login protection like wrong passwords, and the password step clears no counters while the code is still due. "Trust this device" hands out a token `<id>.<secret>` (row in `trusted_devices`, valid 30 days, bound to `token_version`), which the app keeps per account in `localStorage` (`lib/trustedDevice.ts`, beside the session token; MindSift uses no cookies) and sends with the password as `trustTokens`; "end all sessions", any new password and switching the app off end it. A password reset by mail leaves the app on. Switching off and new recovery codes need the password and a code (`confirmWithSecondFactor`, meant to be reused for other sensitive actions). The QR code of the setup is drawn in the browser by `uqr`, loaded only on that screen. Not in the demo. If `SECRETS_KEY` changes, app codes fail and only recovery codes still work.
- **Passkeys** ([api/passkeys.go](../internal/api/passkeys.go), [storage/passkeys.go](../internal/storage/passkeys.go), WebAuthn by `github.com/go-webauthn/webauthn`; browser side [lib/webauthn.ts](../frontend/src/lib/webauthn.ts) without a library, base64url ↔ `ArrayBuffer`, the browser's `parse…OptionsFromJSON`/`toJSON` where present): discoverable credentials with user verification required, so a passkey signs in on its own (`POST /auth/login/passkey/options` + `/auth/login/passkey`, also from the autofill of the login field via `autocomplete="username webauthn"` and `mediation: "conditional"`), answers the second step after the password (`/auth/login/mfa/passkey`, same mfaToken as the codes) and confirms sensitive changes instead of a code (`/auth/mfa/passkeys/challenge`, `confirmWithSecondFactor` takes `code` or `passkeyToken` + `passkey`). The relying party is the host of `BASE_URL`, the only accepted origin `BASE_URL`'s (https, or `http://localhost` for tests); without `BASE_URL`, with plain http elsewhere or an IP address passkeys are off (`/auth/status` → `passkeys: false`, `/auth/mfa` → `passkeysOff` with the reason) and the host is never taken from request headers. Not in the demo. The user handle is the account id; no attestation is asked. Challenges live 5 minutes in memory (`passkeyChallenges`) and are used up by the first answer: registration and confirmation are bound to the account and its `token_version`, the sign-in without password to the ticket handed to that browser (at most 5000 wait, 20 per address, the oldest go first, so anonymous calls cannot fill memory). A passkey answer for the sign-in looks up its account by credential id; failures count in the login protection for that account (unknown passkeys under one shared name), then the same account checks as the password login. Sign count and backup state (`synced`) are stored on every use; a signature counter that is not 0 and does not go up is refused and logged (copied authenticator, or two answers at once). **Two-factor state:** an account has two-factor sign-in when it has a confirmed app or a passkey (`MFAActive`); then the password login asks for the second step, `methods` lists `totp`, `passkey` (only while passkeys are on, otherwise the recovery code is the way in) and `recovery`. Recovery codes and trusted devices belong to the account, not to a method: they come with the first second factor (the app's confirmation, or the first passkey, which returns the codes once) and go only with the last (removing the app keeps them when a passkey is left, removing the last passkey without app takes them along; the settings warn first). Adding a passkey or the app while another second factor is on needs that factor too, so a stolen session and password cannot add a way in that skips it.
- **Required second factor and sensitive changes** ([api/mfa.go](../internal/api/mfa.go)): the system setting `mfaRequired` (`""`, `admins`, `all`) makes the second factor a must. An account it applies to without one still signs in with its password, but `authMiddleware` answers every request of its sessions with `403 mfa_setup_required` except `GET /auth/me` (which says `mfaSetupRequired`), sign-out and `/auth/mfa…`. The places that take a session outside `authMiddleware` refuse it the same way (`mfaSetupRefused`): the live streams `/ws` and `/events`, with the session in the header or with a ticket from before the switch was turned on, and `POST /webhooks/ingest`. The app then shows only the setup (`MfaSetupRequiredView`, loaded with the main views) and an event from the API client brings it up when the switch is turned on during a session. API keys and OAuth stay unaffected. With two-factor sign-in on, a new password or address, deleting the own data or account (`confirmPassword`) need the second factor besides the password, and creating an API key needs it alone (`confirmSecondFactor`), since a key never asks for it. The app does not ask in each form: `withSecondFactor` (`features/settings/user/askSecondFactor.tsx`) runs the change, and on `mfa_required` opens one sheet for a code or the passkey and runs it again (a wrong code asks again). Every change to the second factor (on, off, app or passkey added or removed, new recovery codes, reset by an administrator) is mailed to the account (`notifySecurityChange`), like a new password. Administrators reset somebody's second factor in the user list (`POST /admin/users/{id}/mfa/reset`: app, passkeys, recovery codes and trusted devices go; not the own account, managers only for members); a password reset by mail never does that.
- **Login protection:** Failed attempts (wrong passwords and wrong second-factor codes) are tracked in memory across three buckets: account + IP (3), account (20), IP (30), each within 15 minutes; if one is exhausted, `429` with `Retry-After` is returned for 15 minutes. Unknown usernames count as accounts (prevents user enumeration). A complete sign-in clears account buckets; a password reset (email or admin) clears the lockout. Client IP is only derived from trusted proxies (`TRUSTED_PROXIES`). The same buckets limit registrations (20) and "forgot password" requests (10) per IP per 15 minutes; here every request counts.
- **Invitation codes:** `INV-` plus 100 random bits in Base32. Registration claims the code before the account is created (preventing race conditions / double redemption).
- **Sign-in through an OpenID Connect provider** ([api/oidc.go](../internal/api/oidc.go), [storage/oidc.go](../internal/storage/oidc.go), browser side [lib/oidc.ts](../frontend/src/lib/oidc.ts)): authorization code flow with PKCE (S256), `state` and `nonce`, redirect URI `<BASE_URL>/api/v1/auth/oidc/callback`. Discovery happens on first use and is kept; while the provider is down, `/auth/oidc/start` answers `503 oidc_unavailable` and discovery is tried again at most every 15 s, so the provider never stops MindSift from starting. The ID token is checked completely by go-oidc (signature against the JWKS, refetched when the provider signs with an unknown key; `iss`; `aud`; `exp`, with one minute of clock skew) plus here: the flow's `nonce`, `azp` when there are several audiences or one is given, `iat` not in the future and not older than the flow, `at_hash`. Claims the ID token leaves out come from userinfo (Authelia, Keycloak), whose `sub` must match. **No cookies:** `POST /auth/oidc/start` returns the provider's address and a random `bind` value the app keeps in `localStorage`; only its SHA-256 is stored with the flow (10 minutes, in memory, at most 5000 / 20 per address). The callback sends the browser back to the app's own path with a one-time ticket (`?oidc=…`, 2 minutes, `Referrer-Policy: no-referrer`) or an error code (`?oidc_error=…`); `POST /auth/oidc/exchange {ticket, bind}` gives the session. So the session token never appears in an address, and a callback pushed into another browser (login CSRF) or a ticket from a log is worthless. **Accounts:** tied to (issuer, `sub`) in `oidc_identities` alone. A sign-in never takes over an existing account, not even by an address the provider calls `email_verified` (the former `OIDC_LINK_BY_EMAIL` is gone; still set, it only causes a warning in the log at the start); a first sign-in creates an account (`OIDC_AUTO_CREATE`) with username from `preferred_username` (made unique), display name from `name` and no usable password (`auth.NoPasswordHash`; such accounts take as long at the password form as a wrong password). Its address: verified and free becomes the login address; unverified and free waits as a pending change for its confirmation link (`requestEmailChange`); taken by another account or missing, the account has none (since migration 40 `users.email` is unique only where it is not empty, a partial index, so several accounts may have none). The owner of an existing account links it in the settings (`POST /auth/oidc/confirm` with `link`, after the password and second factor, so a stolen session cannot tie the thief's provider account to it). Locked accounts (disabled, waiting for approval or confirmation) stay locked. `OIDC_ADMIN_GROUP` sets the role at every sign-in from the `groups` claim (Keycloak's full paths `/name` count too), never taking back the last administrator; without a `groups` claim the role stays. **Sessions** started this way have `sessions.via = oidc`: MindSift asks no second factor and `mfaRequired` does not hold them (`mfaSetupMissingFor`). **Sensitive changes** (`confirmWithSecondFactor`, `confirmSecondFactor`, API keys): an account without a password of its own, and an OIDC session without a second factor in MindSift creating an API key, get `403 oidc_confirm_required`; the app (`withSecondFactor`) then offers to sign in at the provider again (`POST /auth/oidc/confirm`, `prompt=login`, `max_age=0`; when the provider sends `auth_time` it must be after the flow began, the identity must be the linked one). The ticket of that return is exchanged by the same session and confirms it for 5 minutes (in memory, per session). A stolen session therefore cannot change the address, set a password, delete or create an API key without signing in at the provider. Accounts with a password keep confirming with it. **Password login off** (`OIDC_PASSWORD_LOGIN=false`): `/auth/login` and the passkey sign-in refuse everybody but administrators with `403 password_login_off` (after a right password only, so it tells nothing more than before), `/auth/register` refuses, "forgot password" mails only administrators, and a password can be set only by administrators; the login shows only the provider's button, `/?login=password` the form (emergency access). Off in demo mode; without `BASE_URL` it stays off and the log says why.
- **JWT and sessions:** HS256, claims `userId`, `email`, `displayName`, `tokenVersion`, `jti`. Each login creates a row in `sessions` (device, IP, last used); `jti` is its ID. A token is only valid if the session is active (not terminated, unused for at most 30 days), the account is active, and `tokenVersion` matches `users.token_version`. If the token is older than 24 hours, the server returns a new one for the same session in the `X-Session-Token` header; the frontend adopts it (`request()` in `lib/api/client.ts`). Active devices stay logged in, unused ones expire after 30 days (`internal/api/sessions.go`). New passwords must be at least 8 characters (`auth.ValidatePassword`). `token_version` is incremented on password changes, role changes, deactivation, and "terminate all sessions".
- **Logout** terminates the device's session; `GET /auth/sessions` lists active devices, `DELETE /auth/sessions/{id}` logs one out. Changing the password or login email requires the current password (`currentPassword`, failed attempts count towards login lockout); a new password logs out all other devices, and the current device receives a new token via `X-Session-Token`. If SMTP is configured, a notification email is sent to the previous address.
- **API keys:** `mindsift_sec_<hex>`, stored as SHA-256, only the prefix remains visible. The key is accepted as a Bearer token or in `X-API-Key`. Scopes `webhook:*` ingest data (`POST /inbox`, `POST /webhooks/ingest`); agent scopes `tasks:read`, `tasks:write`, `lists:read`, `lists:write` apply exclusively to the MCP endpoint (`POST /mcp`, `internal/api/mcp.go`); each tool validates its scope, and `tools/list` only displays permitted tools. All other endpoints respond with `403` for API keys. Keys can only access notes via MCP (`notes:read`: list, read, search; `notes:create`: create new, content as Markdown via `MarkdownToBlocks`; `notes:write`: edit bullets via note sync operations, `internal/api/mcp_write.go`, bullets actively being edited by someone remain untouched), never via REST. Likewise only via MCP: `inbox:read` (open inbox entries) and `inbox:write` (convert or discard via `UpdateThoughtTriage`, only for entries with status `inbox`).
- **OAuth for MCP** (`internal/api/oauth.go`, `internal/storage/oauth.go`): MindSift acts as its own OAuth server using `BASE_URL` for `/api/v1/mcp` (RFC 9728/8414 discovery, dynamic client registration, code flow with PKCE S256, rotating refresh tokens), allowing claude.ai and ChatGPT to connect. The consent screen is part of the app (`/oauth/authorize`, `OAuthConsentView`), as authentication state resides in `localStorage`. Consent creates an entry in `api_keys` (`kind = 'oauth'`); tokens (`mindsift_oat_`/`mindsift_ort_`) are linked to it and valid only at the MCP endpoint, sharing the same permissions and provenance as API keys. Expired tokens and idle connections (`OAUTH_IDLE_DAYS`) are cleaned up by the hourly background job. Disabled in demo mode and when MCP is turned off (`MCP_ENABLED` or admin toggle).
- **Forgot password:** Available only when SMTP and `BASE_URL` are configured (disabled in demo mode; `passwordReset` in `/auth/status`). `POST /auth/forgot-password` returns a uniform response and dispatches the email in the background, rate-limited to once every 2 minutes per account. The link `BASE_URL/?resetToken=…` is single-use and valid for one hour; only its SHA-256 hash is stored (`password_reset_tokens`). `POST /auth/reset-password` updates the password, invalidates all pending reset links for the account, and increments `token_version` (terminating all sessions). The app immediately strips the token from the URL bar.
- **Registration:** Permitted only with an invitation code or when `allow_registration` is enabled. The first account is created via `/auth/setup` and becomes administrator; that endpoint only takes `Content-Type: application/json` (`415` otherwise), so a plain form or `text/plain` POST from another site cannot create the admin of a fresh server. `/auth/register` refuses while no account exists (`403` `setup_required`).
- **Setup code** (`internal/api/setup_code.go`): a server that starts without any account, outside the demo and without `ADMIN_USER`, makes a one-time code (`XXXX-XXXX-XXXX` from 32 unambiguous signs, 60 bits, `crypto/rand`) and writes it to its log (`Setup code: … – enter it in the setup wizard`, at warning level, at error level when `LOG_LEVEL` hides warnings). It stays in memory only, a restart makes a new one. `/auth/status` says `setupCodeRequired`, the wizard asks for it, and `/auth/setup` checks it first (normalized: case, spaces and dashes do not matter; `subtle.ConstantTimeCompare`): missing `403` `setup_code_required`, wrong `403` `setup_code_invalid`, counted per address like failed sign-ins in `loginGuard` (account key `setup:<ip>`, so nobody can lock the real admin out from elsewhere). Once the admin exists the code is cleared.
- **First admin from the environment** (`internal/api/initial_admin.go`): with `ADMIN_USER` and `ADMIN_PASSWORD` set, `CreateInitialAdmin` creates the administrator at startup, before the server listens, while `users` is empty, so a fresh instance is never open to the first visitor. Same rules as the wizard: `ADMIN_USER` must be a valid username (lower-cased; it is also the display name), the password passes `auth.ValidatePassword`, `ADMIN_EMAIL` (optional) must be a bare address. `ADMIN_PASSWORD_FILE` replaces `ADMIN_PASSWORD` for Docker secrets: `config.InitialAdmin.ResolvePassword` reads the file only at this point (trailing `\r`/`\n` removed, everything else counts, as in the variable). Set but unusable (one of the pair missing, too short, invalid name or address, `ADMIN_PASSWORD` and `ADMIN_PASSWORD_FILE` both set, a password file that cannot be read or is empty), the server logs the reason, without the password (a file's path, never its content), and exits with status 1 instead of starting with an open setup. Once any account exists the variables are ignored with an info line, even unusable ones; in demo mode they are ignored with a warning. Without `ADMIN_EMAIL` the account has an empty `email` and signs in with the username; it can add an address in the profile, which counts after the confirmation link like any change of the login address (needs SMTP and `BASE_URL`; without mail an admin can set it directly with `PATCH /admin/users/{id}` and `email`), and until then gets no mails (no password reset either). The wizard's other questions follow after the first sign-in: `system_settings.setup_pending` is `true`, `GET /auth/me` returns `setupPending` to admins, and the app shows `FinishSetupView` (instance name, default language, the server's time zone (preselected from the browser, saved as `timeZone`), sharing mode with the first organization, registration, daily backups, sample data; shared with the wizard in `SetupInstanceSection.tsx`, so later setup questions go there once) until `POST /admin/setup` stores them through the same `applySetupChoices` as `/auth/setup`.
- **Mail in the setup** (`internal/api/setup_mail.go`, `SetupMailSection.tsx`, `SetupSummary.tsx`): both ways of the wizard ask for the mail server when `SMTP_HOST` is not set (the fields of the administration, `SmtpFields.tsx`; optional, stored by `applySetupChoices` into the admin settings) and end with a summary that follows the answers: still open (no mail server, no `BASE_URL`, no address of the admin) and good to know (backup folder and the advice to copy it elsewhere, where the administration is). What the server knows comes from `setupInfo`: in `GET /auth/status` as `setup` while there is no account (without the SMTP host), afterwards from `GET /admin/setup/status` for admins. After `ADMIN_USER` without `ADMIN_EMAIL`, `FinishSetupView` also asks for the admin's address; `/admin/setup` stores the mail server first and then records the address with `requestEmailChange`, so it is confirmed exactly like a changed login address (link to the address, 48 hours, never taken unconfirmed). Without mail server or `BASE_URL` the address waits; when an admin later saves settings that make mails with links possible, `handleAdminUpdateSettings` sends the link of that admin's waiting address (`sendWaitingEmailLink`, past the two-minute cooldown, since none went out before); after setting `BASE_URL` later, the profile's "send link again" does it. The test mail of the wizard goes through `POST /admin/smtp/test` with the unsaved `smtp`; the first-boot wizard has no account yet and points to the administration for it.

## Time Zone

One time zone per server, not per person (self-hosted at home, set once). In effect is the admin's `time_zone` system setting (Administration → Server; IANA name, `''` = not set), else `TZ`, else UTC ([internal/clock](../internal/clock/clock.go): `Resolve`, `Apply`). `main` applies `TZ` first (the demo's sample data needs a zone), `srv.ApplyTimeZone()` then adds the stored setting, and `handleAdminUpdateSettings` calls it again after every save that carries `timeZone`, so a change counts from the next request or tick, without a restart. Names are checked with `time.LoadLocation` (`clock.Load`; `Local` and unknown names give `400 Unbekannte Zeitzone`); a stored name that cannot be read (never expected, the zone data is in the binary) is skipped with a warning.

- **No `time.Local`:** the zone is held in an atomic value, because `time.Local` may not be changed while other goroutines read it. Everything meant for people reads it through `clock`: `clock.Now()`/`clock.Today()` for "now" and "today", `clock.In(t)` for a passed-in instant before taking its day or hour (due dates `domain.ParseDue`/`NormalizeDue`/`HumanDue`, alarms `alarmDue`, the daily summary, `GET /tasks?due=`, search `due:`, backups and their file names, next occurrences `NextDueDate`, greetings and dates in mails, demo sample data, download file names). Instants (timeouts, expiry, UTC timestamps in the database) keep `time.Now()`.
- **Schedulers** compute on every tick from `clock.Now()` (alarms and notifications every minute, backups every minute against `backup_time`), so they follow a new zone at once. Moving the zone can move "today" for the backup: the scheduler compares the date of the newest snapshot with today's date in the new zone.
- **API:** `GET`/`PUT /admin/settings` carry `timeZone` and the read-only `serverTime` (`zone`, `source`: `setting`/`env`/`default`, `now` in RFC 3339 with the offset, `fallback`: the zone without the setting). The administration shows the server time from `now`, moved on locally, so it reads right whether the browser knows the zone or not.

## Languages

- **Frontend:** i18next (`frontend/src/i18n`). Texts live in `frontend/src/locales/<code>/<area>.json`; every language is a chunk of its own, German included, so the start chunk carries no texts. German is the fallback for keys a language lacks: before the first render `main.tsx` waits for the start language (`startLanguage`: with a stored session the one shown last on the device, else the browser's, else `<html lang>` from the server) and German together (`startI18n`), so neither raw keys nor German before another language flash up; the index.html logo stays meanwhile, and the first `/auth/status` request goes out at the same time (`prefetchAuthStatus`). The app's chunk of a stored session starts loading only after that first render, as evaluating it first would hold the render up. The build preloads the German chunk next to the start chunk (`modulepreload`, vite.config.ts) and the service worker keeps all of them for offline starts. App switches to the account's or the server's language once the server has answered. The areas (namespaces) are listed in `NAMESPACES`; a test compares them with `locales/de/index.ts`. The help is one content file per language (`features/help/content/<code>.tsx`), each a chunk of its own that loads when the help first opens in that language (German if it cannot). Dates, times and sorting go through `lib/format.ts`. A test checks that every language has the German keys and placeholders and that every `t('…')` in the code exists; the ESLint rule `i18next/no-literal-string` rejects fixed text in JSX.
- **Language choice:** `users.language` (empty = browser, then default language; accounts from before the choice are `de`), the admin's `default_language` system setting, `DEFAULT_LANGUAGE` as start value. `internal/i18n` lists the supported codes and matches `Accept-Language`.
- **Backend:** server texts are written in German in the code; `internal/i18n/messages_<code>.go` holds a catalog per language keyed by the German text, with `{name}` placeholders (`i18n.T`). `languageMiddleware` puts the language of the answer in `Content-Language`, where `writeError` and `tr` read it: `Accept-Language` when MindSift speaks it, else the admin's default language or `DEFAULT_LANGUAGE`, else English (`answerLanguage`; the sign-in screen, `index.html` and new accounts keep German as the last fallback, `requestLanguage`); MCP and OAuth use English. Errors carrying values (a folder name) are `i18n.Localizer`s and go through `trErr`/`i18n.Text`. A test scans the code for German texts in error answers and fails when a catalog lacks one. Messages to a person (mails, push, Discord/webhook alarms, the daily summary, notifications) and texts the server writes into their data (journal titles, board columns of new task lists, untitled notes, export folders) use their language (`userLanguage` in the API, `MessageLanguage` in the store: own choice, else the default language); dates and times in them come from `internal/i18n/format.go`. Invitations go out in the language of the one inviting.
- **Adding a language:** locale files and help content for the code, an entry in `LANGUAGES` (`frontend/src/i18n/index.ts`) with a loader, the code in `Supported` (`internal/i18n/i18n.go`) a server catalog in `internal/i18n/messages_<code>.go`, registered in `catalogs` (`messages.go`), and date formats in `internal/i18n/format.go`.

## Media in Notes

Images and audio files are stored in `$DATA_DIR/media/<docId>/<id>.<ext>`, tracked in the `media` table (Migration 5, `internal/storage/media.go`). A block references them via its content, e.g. type `image` with `![Caption](media:med_…)`; this allows references to pass through synchronization, undo, and conflict resolution without altering the sync model. Uploading (`POST /documents/{id}/media`) requires write access to the note; reading (`GET /media/{id}`) requires read access to either the file's note or any note whose blocks reference it (copied blocks). File formats are detected by content inspection (JPEG, PNG, GIF, WebP; WebM, Ogg, MP3, WAV, M4A); SVG and other formats are rejected; responses include a strict CSP with `sandbox`. The server fetches external images once (`POST /documents/{id}/media/fetch`, https only, public IP addresses only as with webhooks, disabled in demo mode). Quotas/limits: `MEDIA_MAX_IMAGE_MB`, `MEDIA_MAX_AUDIO_MB`, `MEDIA_QUOTA_MB`, and `MEDIA_DEMO_MAX_MB` in demo mode. Backup ZIP (`Obsidian/attachments/<id><ext>`, the vault next to the JSON; older backups `media/<id><ext>`, still read on import) and Markdown archives (`attachments/`, embedded as `![Caption](../attachments/…)` relative to the note) include the files belonging to the user's notes; during import, they are assigned new IDs. Obsidian import handles images and audio embedded alone in a bullet (`![[file.png]]` or `![](path/file.png)`); other files are listed as skipped in the preview. Compaction (every 6 hours) deletes files no longer referenced by any block (deleted bullets not yet purged count too; the operation log does not), at the earliest one day after upload. Which bullets point to a file is looked up in `block_refs` ([database.md](database.md)), not by searching block text. Demo reset empties `media/`.

## Restructuring Notes

`internal/storage/restructure.go`: **Extract branch** reads the subtree and creates a new note whose first bullet is the extracted bullet itself (its children below it); the title comes from the bullet's text without hashtags, or "New note" for bullets without usable text such as drawings, images or code (ensuring a unique title, inheriting direct and group shares; the original note's owner receives write access). The editor replaces the branch in the original note with `[[Title]]` as a dedicated change through the sync engine, avoiding collisions with pending unsent inputs and allowing Ctrl+Z to undo it; `/extract/undo` moves the newly created note to the trash. **Move branch** copies a bullet with its children to the end of another note through the target's sync operations and points tasks and subtasks linked to these checkboxes at the copies (`converted_ref_id`, `SubTask.BlockID`); like extracting, the editor removes the branch from the source itself (dragging the bullet onto a note in the sidebar, or choosing an existing note in the extract popover, which leaves a link to the moved bullet behind), and `/move/undo` reverses the target side when the editor undoes its own change. **Merge notes** appends the source note as an `h2` heading with its bullets as children to the target note (also via sync operations, updating active editors in real time) and moves the source note to the trash; "Undo" deletes the heading along with its sub-bullets and restores the source note. The action runs under the editor client's ID (`clientId`), preventing its own block locks from interfering. Images and audio recordings continue to function because access is checked against notes displaying them.

## Collaboration: Live Drawing

Several people draw in the same drawing bullet at once, in the manner of Excalidraw (no Yjs, no new dependency). Server: [internal/drawlive/](../internal/drawlive/session.go) (sessions, merging) and [internal/api/drawlive.go](../internal/api/drawlive.go) (messages, rights, lease); browser: [lib/drawing/live.ts](../frontend/src/lib/drawing/live.ts) (merging) and [useLiveDrawing.ts](../frontend/src/features/workspace/drawing/useLiveDrawing.ts) in the drawing editor. Messages: [api/websocket.md](api/websocket.md#live-drawing).

- **Channel:** drawing along needs a WebSocket (`DRAW_*` messages both ways). Without one (SSE or long polling behind a proxy) a person can watch live but not draw along. Opening a drawing to edit with a WebSocket starts a session (alone until someone joins); without one and without a running session, editing works alone as before (the bullet locked for the others).
- **Merging:** every element has a version `ver` (already stored in the block) and in the session a random `nonce`. A change raises the version; the browser sends changed elements every 50 ms at most. The higher version wins, a tie goes to the lower nonce, on the server and in every browser alike. Deleting sends a tombstone (`{id, ver, nonce, deleted: true}`) that stays until the session ends, so a late change cannot bring an element back. The order of the elements (to front, to back) is a list the last change sets; the grid travels with the changes.
- **Gestures:** an element being dragged, resized or written in keeps its local state until it is let go; changes of others to it wait. On letting go, the own result goes out first with a version above everything seen (it wins), then the waiting changes merge as usual. Changes of others also go into the undo steps, so Ctrl+Z only takes back own changes (as new versions).
- **Host:** whoever started the session saves with "Fertig" or discards for everyone (with a question). If the host goes (tab closed, connection lost), the person drawing longest takes over; everyone sees the new host. The others have "Verlassen" instead of "Fertig". "Fertig" ends the session: the host gets the final state from the server and saves it through the normal note sync as one change (undo of the note as before); the bullet's lease goes straight to the host's note (`clientId` in `DRAW_DONE`), so the save is no conflict copy. Everyone else sees the end.
- **Lease:** while anyone draws, the session holds the bullet's lease (holder `draw:<blockId>`, renewed every 5 s) and takes it over from clients of the people drawing. The note shows "Live-Zeichnung: Anna, Ben" instead of "Anna bearbeitet" (`leases.others[].live`); nobody else writes into the bullet meanwhile. Someone editing alone without WebSocket keeps the bullet: a session cannot start then.
- **Nobody left:** if everyone leaves without "Fertig", the state stays in the server's memory for 10 minutes; opening the drawing again with the same block content resumes it. Such a session gives way earlier when room is needed (limits below), the oldest first. Each browser keeps its local draft as before.
- **Server restart:** sessions are in memory only. Browsers that were drawing join again with their whole state (elements with versions and tombstones); the server merges by version, the first one back is host.
- **Rights and limits:** drawing along needs write access to the note, watching read access; rights are checked on joining and every 5 s. At most 5000 elements (and as many tombstones), 1 MB per session, 64 kB per element, 40 changes and 30 pointer messages a second per connection. Across sessions (`drawlive.MaxUserSessions` and others): a connection draws in one drawing at a time (joining another leaves the previous one); a person keeps at most 8 sessions going (those they draw in plus those they left last; drawing along in someone else's running session is always possible), the server at most 256 sessions and 32 MB in all; joining and watching at most 2 a second per person (bursts of 20). Over a limit, sessions everyone left give way first (the person's own, then anyone's); only then is the join refused (`too_many`, `busy`), and the editor shows the drawing read-only with a notice. Leaving over REST (`/watch` with `leave`) only takes the caller's own connection. Public links have no sessions.
- **Display:** pointers of the others with their name in their person colour (`lib/userColor.ts`), on touch a dot while the finger is down; their selection framed in that colour; an avatar stack of everyone drawing and watching with the host's name in the editor's bar.
- **Saved content:** `ver` stays in the block as before (the server's `internal/drawing`, Mermaid import, export and MCP ignore it); nonces and tombstones are never saved.

## Notifications

`internal/api/notify.go`, `internal/storage/notifications.go` (Migration 7). Each user selects notification channels per event type—personal email (the confirmed login address), personal Discord webhook, custom webhook (`customWebhookUrl`, JSON via POST), and Web Push to registered devices (`internal/api/push.go`, Migration 9, table `push_subscriptions`; devices unrecognized by the push service (404/410) are pruned)—stored as JSON in `users.notification_settings` (`GET /auth/me`, `PATCH /auth/settings` → `notificationSettings`). Events: `due` (due date alarm, dispatched immediately via the alarm ticker), `mentioned` (someone @-mentioned the user in a task's description or subtasks, or in a bullet; `{{mention:<user id>}}`, only a new mention notifies: tasks compare before/after, bullets keep their last count in `block_mentions`; readers outside the app get `@Name`: export, MCP content, search snippets; public pages `{{mention:hidden}}`), `shared` (note, folder, task list, or list shared; all group members notified for team shares), `assigned` (someone else assigned a task to the user; only people newly added), `taskCreated` (a task was added to a shared task list: created there, made from an inbox entry or moved there; off by default), `taskDone` (task completed in a shared task list), `watched` (any update to a watched task, `task_watchers`, `POST/DELETE /tasks/{id}/watch`; the text names every changed field, or the one change as a sentence; changes made in a note through a linked checkbox count too, `afterDocChange` gets the task states before `ReconcileDocTaskLinks`). A queued event may carry a `key` (task and kind of change): of several queued events with the same key only the latest is sent, so typing in a note does not produce a line per pause. **Notification center:** `notify()` first stores every event for each recipient but the actor in `center_entries` (regardless of channels, pause or demo mode) and sends `NOTIFICATION` over the WebSocket; the bell (`NotificationBell`; phones in the header, desktop in the navigation rail) lists them, a click opens the task, note (at the bullet) or list. A watched task keeps one entry (`watched:<id>`; two different changes merge into "… changed …"), the alarm ticker adds a due entry once per task, recipient and due date (it runs in demo mode too, without sending). Entries go after 14 days (`PruneCenter`). Everything except `due` is queued in `notification_queue`; a minute-interval job dispatches a bundled digest per user once the oldest event reaches `NOTIFY_DIGEST_MINUTES` (default 5) in age (email as text + HTML, Discord as an embed limited to 10 lines, custom webhook as JSON `{"event":"digest","heading","items":[{"kind","title","text"}],"link","timestamp"}`; due tasks are dispatched individually as `{"event":"task_due",…}`), discarded after 3 failed attempts. Actions performed by the user never trigger notifications for themselves, except for watched tasks with `includeOwnWatched`. A muted task list (`task_list_mutes`, `PUT /task-lists/{id}/mute`) sends its members no list-wide events (`taskCreated`, `taskDone`, due date of unassigned tasks); assignments, mentions and watched tasks still come. `paused` mutes everything, including alarms. **Daily digest:** at the configured time (server timezone, within a 30-minute window, once daily), summarizes overdue, today's, and tomorrow's open tasks along with the count for the next 7 days; no due tasks → no message. Jobs are disabled in demo mode.

## Link Previews

Bullets containing a bare https URL display a card above them (`LinkPreviewCard`, `lib/linkPreview.ts`). `GET /link-preview?url=` fetches the web page server-side with the same security checks as webhooks (https only, no private/internal IP addresses, redirects verified), parses `og:*`/`twitter:*`, `<title>`, `description`, and the icon from `<head>` (max 1 MB HTML, image 2 MB, icon 100 KB, no SVG), and caches everything in `link_previews` (Migration 6): successful fetches for 7 days, failed/empty fetches for 1 day, pruned after 30 days. Images are served via `GET /link-preview/{key}/image|icon` with authentication. Maximum 300 requests per IP per 15 minutes (cache hits do not count). Dismissing a card converts the bare URL into `[Title](url)` (named markdown links do not show preview cards), syncing the preference with the note; "Show link previews" under Appearance is a per-device setting. Disabled in demo mode.

## Speech Recognition

Admins configure it via environment variables (`STT_*`, see above); Administration → Server & Sharing displays the active mode, Whisper server health, and provides a test recording tool. When a Whisper server is configured, each user can choose between Whisper (default) and browser recognition under Account Settings → Voice Input (`users.voice_input`), unless `STT_ALLOW_BROWSER` is set to false; `/auth/status` indicates `voice.browserAllowed`, and the app applies the preference in `lib/voice.ts`. Under Voice Input everyone also picks the spoken language (`users.voice_language`): `auto` (default, also when nothing is chosen: Whisper detects it per recording, no `language` sent; best for mixed sentences like German with English terms), `app` (the app language) or any of Whisper's languages (`lib/voiceLanguages.ts`, names via `Intl.DisplayNames`); the browser's recognition uses the chosen language as `lang`, and the app language for `auto`. All microphone buttons (Quick Dump bar, mobile capture sheet, holding the + button, the microphone in input fields such as a task's title and notes, `/diktat`) share the `useVoiceInput` hook (`frontend/src/lib/voice.ts`, `useVoiceInput.ts`): `server` sends the recording in pieces while speaking (every ~8 s or at a short pause, `chunked`, on by default), so the text arrives while speaking and a long dictation is not transcribed all at once at the end; after stopping, only the last piece is still "Transcribing...", `browser` streams transcribed text in real time while speaking and finishes after 5 s of silence, and `off` or an unsupported browser hides the microphone button. In server mode, waveform bars reflect real microphone levels (`VoiceWave`), and recordings automatically stop after `STT_MAX_SECONDS`. The browser records using `MediaRecorder` (WebM/Opus, or MP4/AAC in Safari) and POSTs audio to `/voice/transcribe`; MindSift proxies it to `STT_URL/v1/audio/transcriptions` (`model`, `language` from the person's setting) and returns only the transcript. Nothing is stored or logged except errors (`internal/api/voice.go`). On startup, MindSift waits for the Whisper server and initiates model download if not already cached (`POST /v1/models/<id>` on speaches).

`docker-compose.yml` includes the `whisper` service (speaches 0.8.3, CPU) as a commented-out block: uncomment it, set `STT_URL=http://whisper:8000` in `.env`, and run `docker compose up -d`; model data resides in `./whisper` (directory owned by UID 1000). Benchmark on a 16-core desktop CPU (int8) for a 4-second sentence: `Systran/faster-whisper-small` takes 1.6 s, `deepdml/faster-whisper-large-v3-turbo-ct2` takes 8 s with significantly higher accuracy (RAM approx. 1 GB vs. 2 GB). On shared vCPUs, expect higher latency.

**Choosing a model:** the two models the install script offers (large-v3-turbo, small) are OpenAI's multilingual Whisper models and work well in German, English, Spanish, French and Italian. Any Whisper model in CTranslate2 format runs too, for example one fine-tuned for a single language: [list of compatible models on Hugging Face](https://huggingface.co/models?pipeline_tag=automatic-speech-recognition&library=ctranslate2&sort=downloads) (the same list speaches uses; add a language to the search, e.g. [German](https://huggingface.co/models?pipeline_tag=automatic-speech-recognition&library=ctranslate2&sort=downloads&search=german)). Put the model's name into `STT_MODEL` in `.env` (e.g. `Systran/faster-whisper-small`) and run `docker compose up -d`; MindSift downloads it by itself. Larger models recognize better but need more RAM and time.

## Background Job: Alarms

`startAlarmTicker` checks every minute for all open tasks with due dates and their recipients (`storage.TaskAlarmRecipients`): a personal task or one in a list nobody else sees alarms its owner; in a shared list the assignees, or every member who did not mute the list when nobody is assigned. Once the alarm time is reached (due time or 9:00 AM for all-day tasks, minus the recipient's lead time, evaluated in the server's time zone, see "Time Zone"), it sends notifications across the recipient's channels (`email`, `discord`, `webhook`, `push`) and marks the alarm as sent for that person (`task_alarms_sent`) once at least one channel succeeds. A task's own **reminders** (`thoughts.reminders`, e.g. `20160,0`, Migration 32) replace the lead time for all its recipients: one alarm per reminder, each kept as sent per person (`task_alarms_sent.reminder`, `-1` = the lead time); whole days and the month go by the calendar (`domain.DueAlarmAt`), so a change of daylight saving time moves nothing. Alarms a day or more ahead name the due date ("is due on …") instead of "due now"; the webhook gets `remindBeforeMinutes`. The next occurrence of a repeating task keeps its reminders. After 3 unsuccessful attempts for a person, it stops retrying. A new due date or reopening clears all of them (`alarm_sent` 1 → 0, trigger). The daily summary uses the same recipients. A task created in a shared list starts out assigned to its creator. Details and limitations: [modules/tasks.md](modules/tasks.md).

## Background Job: Note Sync Compaction

`startCompaction` runs at startup and every 6 hours thereafter: purges expired leases and in-memory sessions, log entries older than 30 days (private notes: 7 days), tombstones older than 30 days, and idempotency results older than 90 days. Details: [database.md](database.md#note-log-compaction).

## Build

```
Stage 1  node:26-alpine   tsc, vitest, vite build            → frontend/dist
Stage 2  golang:1.27      go vet, go test, go build          → /app/mindsift (dist is embedded)
Stage 3  alpine:3.24      binary only, ca-certificates, tzdata
```

**Third-party licenses:** the build writes `/app/THIRD_PARTY_LICENSES.txt`. Stage 1 lists the production dependencies of `package-lock.json` with the license files of their installed packages (`ci/third-party-licenses-npm.mjs`), stage 2 adds the Go modules the server imports on the target platform (`go list -deps`) with their license files and Go's standard library (`ci/third-party-licenses.sh`); a Go module without a license file fails the build. Neither needs an extra tool. The release archives carry the file next to the binary. The server serves the file next to its binary at `/third-party-licenses.txt` (`internal/api/licenses.go`, 404 without it, e.g. in development), linked in *About MindSift*; the service worker keeps only HTML answers as the offline start page, so opening it does not replace the app.

**Platforms:** the public images are built for `linux/amd64` and `linux/arm64`. Stages 1 and 2 run on the platform of the building machine (`FROM --platform=$BUILDPLATFORM`) and the binary is cross-compiled (`GOOS`/`GOARCH` from `TARGETOS`/`TARGETARCH`; SQLite is pure Go, so no C toolchain is involved). The frontend build and the tests therefore run once, however many platforms are built. Only stage 3 exists per platform, and its one `RUN` step runs emulated (QEMU) for arm64. The GitHub workflow builds with `docker buildx` and pushes both platforms as one image; a release is retagged by copying that image inside the registry (`docker buildx imagetools create`), and after every push the workflow fails if a tag lacks a platform. The private Gitea pipeline builds for the platform of its runner only. A plain `docker build` or `podman build` builds for the local machine as before; `--platform linux/arm64` builds the other one where QEMU is registered (`qemu-user-static`).

**Health check:** stage 3 declares a `HEALTHCHECK` (busybox `wget` on `http://127.0.0.1:$PORT/api/v1/health`, every 30 s, timeout 5 s, start period 10 s, 3 retries; `-Y off` keeps an `HTTP_PROXY` out of it). It runs as the user of the container (root unless `--user`/`user:` is set), not as the user the entrypoint switches to, and needs no files. Docker reads it from every image; podman only from images in Docker format (`podman build --format docker`), not from OCI images such as its own default builds or the multi-platform images `docker buildx` publishes. `docker-compose.yml` therefore repeats it as `healthcheck:`.

**Release binaries:** `ci/release-binaries.sh` copies `/app/mindsift` and `/app/THIRD_PARTY_LICENSES.txt` out of the images of a version tag, once per platform, and `release.yaml` attaches them to the release as `mindsift-<version>-linux-<arch>.tar.gz` with `SHA256SUMS`. They are the binaries of the images, not a second build, and need nothing beside them: the frontend is embedded, the data goes to `./data` (`DATA_DIR`). Started on its own, the server sets the same umask as the entrypoint of the container (`cmd/server/umask_unix.go`: new files 0600, new folders 0700).

**Image tags (CI):** Push to `dev` → `:dev`; Push/merge to `main` → `:latest`; Git tag `v*` (e.g. `v1.2.0`) → `:v1.2.0` and `:stable`; pre-releases (`v1.2.0-rc.1`) only `:v1.2.0-rc.1`, `:stable` remains unchanged. Other branches are not built.

**Security scan (CI):** `ci/trivy-scan.sh` runs Trivy on the image before it is pushed and fails on known HIGH/CRITICAL vulnerabilities that have a fix, or on leaked secrets. It runs for every tag, and for branches only when `Dockerfile`, `go.mod` or `go.sum` differ from the image last published under that tag (label `io.mindsift.deps`, decided in `ci/build-plan.sh`). `.github/workflows/security-scan.yaml` scans the published `:stable` and `:latest` every Monday and reports to GitHub's security tab. Both scan the amd64 image; the arm64 image gets the same Alpine packages and the same Go modules.

**Versioning:** From v0.6.0 onwards following [Semantic Versioning](https://semver.org/spec/v2.0.0.html): `MAJOR.MINOR.PATCH`, three-part tags prefixed with `v` (`v0.6.0`, `v1.0.0-rc.1`). While major version is 0, breaking changes (API, data formats, configuration) increment the minor version, bug fixes increment the patch version. Any user- or operator-facing change is recorded in [CHANGELOG.md](../CHANGELOG.md) under "Unreleased" (following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)); upon release, the section becomes the version heading with date, and `frontend/package.json` is updated with the version number.

The displayed version (phone header, expanded desktop rail, footer) is injected by build arg `APP_VERSION`: CI supplies the tag name on Git tags (`v0.6.0`), otherwise the app displays the version from `frontend/package.json` with `-dev` suffix (`v0.6.0-dev`). Implemented in `frontend/vite.config.ts` and `frontend/src/version.ts`.

Tests run during the image build of GitHub `main` (frontend: `npm run test:run`, backend: `go test ./...` in the build stage, which has no `node_modules`; `TEST_REFS` in the workflow), and failures abort that build; other builds skip them, because `ci/local-checks.sh` runs them before every push. Frontend tests are located under `frontend/src/**/__tests__/` (Vitest + jsdom + Testing Library, setup in `frontend/src/test/setup.ts`).

## Container User

The image runs MindSift as the unprivileged user `mindsift` (uid/gid 1000). [ci/entrypoint.sh](../ci/entrypoint.sh) starts as root, hands `DATA_DIR` (and the folder of a database moved with `DATABASE_URL=sqlite://…`) to that user when something there does not belong to it yet (installations from before v0.87.3, whose files belong to root), and then starts the app with `su-exec`. Started with `--user`/`user:`, the entrypoint only starts the app; the data folder must then already belong to that user.

## Background Job: Backups

[backups.go](../internal/api/backups.go) / [backup.go](../internal/storage/backup.go): When "Automatic Backups" is enabled in admin settings, the job runs once daily at the configured time (`backup_time`, server time zone; missed runs due to restarts are made up on the same day). Whether today's backup already ran is read from the newest snapshot, so moving the time does not add or skip a day: after a backup at 03:00, moving the time to 01:00 waits for tomorrow; without a backup yet today, moving it to a time already past starts one within the next minute:
- `backups/system/mindsift-db-YYYY-MM-DD-HHMM.db.gz`: Complete database dump via `VACUUM INTO` (consistent snapshot even while writes occur), gzipped.
- `backups/system/pre-migration-<id>-YYYY-MM-DD-HHMMSS.db.gz`: the same dump, written at startup before pending schema migrations, independent of this job and its setting; the last three stay ([database.md](database.md#migrations-and-startup-cleanup)).
- `backups/users/<id>/mindsift-backup-….zip`: The same ZIP as generated by "Download Backup" for every active user account, including images and audio from personal notes. Next to `mindsift-backup.json` it holds the whole workspace as an Obsidian-compatible Markdown vault (`Obsidian/`, as in the Markdown export, with the images, audio and drawings in `Obsidian/attachments/`), so the data can be read without MindSift. Restoring prefers `mindsift-backup.json` when it is present and takes the media from the vault (or from `media/` in older backups).
- **Note:** The database dump does not include media files. When backing up the host server, back up the entire `data/` folder (database, `media/`, `backups/`).
- Files older than `backup_retention_days` (default 3) are pruned subsequently. Files are written via `.part` and renamed atomically; partial backups never appear in the list. The API only serves files matching this exact naming scheme.
- **Deleted accounts:** when an admin or user manager deletes an account, `backups/users/<id>` moves to `backups/deleted/<id>` (with `account.json`: name, e-mail, time of deletion) and stays for `backup_retention_days`; admins see and download these under Administration → Server & Sharing → Backups (`GET /admin/backups/deleted`), the person imports one into a new account. The hourly cleanup removes them afterwards. An account deleted by its owner loses its backups at once.
- **Setup:** `backup_enabled` is off in a new database, but the setup wizard asks (`SetupInstanceSection.tsx`, preselected on with `03:00` and 3 days, the time in the server's time zone that the same step asks for, the defaults in `storage/backup.go` and `frontend/src/lib/backupDefaults.ts`), on both ways: `/auth/setup` and, after an admin from `ADMIN_USER`, `/admin/setup`. `setupChoices.check` refuses a time other than `HH:MM` or a retention outside 1–365 days with `400` (`storage.ValidBackupTime`, `ValidBackupRetentionDays`), where the admin settings silently keep the stored value. The scheduler reads the settings every minute (`backupDue`), so the first run needs no restart; set up after the chosen time on a day without a backup, it runs within the next minute.
- Backup schedules are disabled in demo mode. Restoring a database snapshot: stop the container, replace `mindsift.db` with the uncompressed file, start the container. Users can restore their individual backups in account settings, optionally scoped to individual modules (notes, tasks, lists, inbox, themes).

## Background Job: Retention

[retention.go](../internal/storage/retention.go), initialized in `internal/api/done_cleanup.go`: Each user can configure retention in Account Settings → Retention per domain: 7, 14, 30, 90, 365, or 730 days, or never. Every hour, completed tasks exceeding the retention period are moved to the tasks trash (`trashed_tasks`); items in the tasks trash, triage trash (discarded thoughts), notes trash, and checked-off list items are permanently purged once expired. In shared task lists, lists, and notes, the owner's retention period governs. Items already completed or trashed when retention was introduced count from that point in time (`system_settings.retention_since`). Setting `RETENTION_ALLOW_NEVER=false` (or disabling "Allow permanent retention" in Administration → Server & Sharing) removes the "never" option; existing "never" selections fall back to the section default.

## Offline (PWA)

- **Service Worker** ([public/sw.js](../frontend/public/sw.js)): Network-first strategy for navigation requests with the last-cached `index.html` as fallback, assets under `/assets/` (content-hashed names) served cache-first, icons and manifest served stale-while-revalidate. API requests are never intercepted. At install it loads every file of the build (`PRECACHE`, written into `sw.js` by a plugin in `vite.config.ts`), so the app starts offline after the first visit; every release is a new worker. Cache lookups for assets ignore `Vary` (the server sends `Vary: Origin`, module requests carry an Origin header, the preload does not). Files of the current build always stay; of earlier builds only the newest (at least 40) for pages still open on an old version. Stale caches are invalidated when a new `VERSION` activates. A missing app chunk while online (a release replaced it) reloads the page, at most once a minute; offline the app offers to try again.
- **Read Cache** ([lib/offline.ts](../frontend/src/lib/offline.ts)): Every successful GET response is cached per user in IndexedDB (`mindsift-offline`). When offline, `request()` returns the latest cached response, allowing the app to open offline in an authenticated state with thoughts, tasks, and lists accessible. Exceptions: streams, long polling, note sync (dedicated storage, [modules/collaboration.md](modules/collaboration.md)), exports, search. Logging out purges cache and queues, and the stored notes (see below); a rejected session (401) purges cache and queue but keeps the stored notes, so text typed offline survives an expired session.
- **Outbox Queue:** Thoughts captured offline (`POST /inbox`) and checked/unchecked tasks or list items (`PATCH`) are queued in `localStorage`; rapid toggles only send the final state. Queued actions are replayed in order upon the `online` event, on app launch, and every 30 s while items remain pending; requests rejected by the server with 4xx errors are dropped. Other modifications still require an active connection.
- **New Version Detection:** Each build writes `version.json` (version and build commit) next to `index.html`, never cached. The app compares it with its running version when switching back to the tab/app, every 5 minutes, when the browser is online again, and after server restarts (reconnected real-time channel), displaying "New version available" with an "Update now" prompt ([lib/useUpdateCheck.ts](../frontend/src/lib/useUpdateCheck.ts)).
- **Per-Tab State:** Active view (triage, workspace, tasks, etc.), active note, and selected list are preserved in `sessionStorage` ([lib/viewSession.ts](../frontend/src/lib/viewSession.ts)) across page reloads.
- **Status Indicator:** A banner above the bottom navigation displays "Offline" along with the pending change count, or "Syncing...".
- **Connection Status at the Avatar** ([lib/useConnectionState.ts](../frontend/src/lib/useConnectionState.ts)): Determined by the app-wide real-time connection status rather than `navigator.onLine`, reliably detecting server outages. WebSocket or SSE: **online**. Long polling only (e.g. proxy buffering SSE): **degraded**, updates arrive with slight delay. If all connections drop for more than 4 s (smoothing over initial launch and momentary reconnects), the app pings `/api/v1/health` (then polls every 15 s): if the server responds, status is **degraded**, otherwise **offline**. If device network is disconnected, status becomes **offline** immediately. Rendered as a green/yellow/red dot on the avatar (phone header, desktop navigation rail); the expanded rail also shows the status below the user name.

### Dynamic OpenGraph URL Injection

Messenger crawlers (especially WhatsApp) often fail to resolve relative image URLs in `og:image`. When serving `index.html`, the Go SPA handler in [`internal/api/server.go`](../internal/api/server.go) dynamically substitutes relative paths (`/og-image.png`, `og:url`) with the absolute server origin (`scheme://host`), determined via `X-Forwarded-Proto` and `X-Forwarded-Host` or `req.Host`.
