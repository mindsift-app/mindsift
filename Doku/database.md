# Database

SQLite file `mindsift.db` (default: `$DATA_DIR/mindsift.db`), opened with `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=10000`, `journal_size_limit` of 16 MB (the WAL grows to the size of the largest transaction, e.g. an import, and is cut back to 16 MB after the next checkpoint instead of staying that large), and at most 8 connections. **Rule:** a function never needs a second connection while it holds one: no query inside a loop over open `rows` and none between `Query` and the loop (read the rows, close them, then query on), and no `s.db` call inside a transaction (use the `tx`). Otherwise enough parallel requests use up the pool and every request waits forever (load test 2026-11-05). The tests run with `DB_MAX_CONNS=1` in the build, so such code hangs there at once (`TestQueriesNeedOnlyOneConnection` covers search, list and folder shares and task lists). Reads that must be consistent but not block writers (note snapshot, sync log) use `readConsistent`: one connection with a deferred `BEGIN`, a WAL snapshot without the write lock that `s.db.Begin()` takes (`_txlock=immediate`). The schema is constructed in `Store.migrate()` ([sqlite.go](../internal/storage/sqlite.go)): first `CREATE TABLE IF NOT EXISTS`, followed by a list of idempotent `ALTER TABLE`/`CREATE` statements for older databases. IDs are text prefixed with type identifiers (`usr_…`, `th_…`, `tkl_…`, `lst_…`, `tls_…`, `blk_…`, `doc_…`) followed by 96 random bits encoded in hex; older records have shorter IDs (40 bits).

### Note Text Stored Once <a id="note-text-stored-once"></a>

Since Migration 44 ([note_storage.go](../internal/storage/note_storage.go)) the text of a bullet is stored once, in `blocks.content`. Before, 17.8 MB of note text grew the database by about 220 MB: every change wrote the whole note three more times into its `documents` row, the log kept the full text of every change for its retention period, and the search index kept a copy of its own.

- **Log texts** ([doclog.go](../internal/storage/doclog.go)): `doc_ops.content_ref` says where the text of an `insert` or `set_content` entry is. `0`: in the payload (other kinds, entries from before the migration, bullets purged for good). `1`: the newest text entry of a bullet stores no text, it is the bullet's current `blocks.content` (nothing else changes that column). `2`: when the next text entry of the bullet arrives, the previous one becomes a delta against it, `{"p": bytes shared at the start, "s": bytes shared at the end, "m": what stood in between}` in the payload (`"mb"`, base64, for a part that is not valid UTF-8). Typing changes a few characters, so an entry keeps those instead of the whole bullet. A delta is always relative to the next newer text entry of the same bullet; the log is only cut from the old end, so that entry is still there. Reading the log (`GetDocOpsSince`) puts every text back, from the newest entry backwards, so clients get exactly the effects as before; the partial index `idx_doc_ops_text` finds the entries of a bullet after a page. If a text cannot be put back (it should not happen), the client is told to reload the snapshot (`resync`), as for a compacted log. Before compaction purges a bullet, the texts of its remaining entries are written back into their payloads.
- **Search index** `documents_fts`: an FTS5 table with external content, without a copy of the text. Its rows are those of the view `documents_fts_source`: the titles of notes outside the trash (key `documents.fts_rowid`, -1, -2, …) and the live bullets (key `blocks.fts_rowid`, 1, 2, …), with the text the search sees (`blockSearchText`: drawings by their words, tables without pipes). FTS5 reads the text there for snippets. The keys are stored, so they do not depend on rowids. The triggers `trg_documents_*` and `trg_blocks_*` hand the index each change with the values it was given before (FTS5 needs exactly those to remove a row) and skip changes that do not touch the searched text (ticking, folding, moving). They look up rows by key, where the earlier triggers searched the whole index for every changed bullet. A change to what is indexed therefore needs `INSERT INTO documents_fts(documents_fts) VALUES('rebuild')`; FTS5 refuses virtual tables in the view, so it uses no `json_each` (the words of a drawing are read with a recursive CTE). Integrity check: `INSERT INTO documents_fts(documents_fts, rank) VALUES('integrity-check', 1)`.

`lang` is the language of a code block; for a `table` it holds the line mode (`''` inner lines fading out, `grid` all lines with a frame, `header` the line below the header and the column lines). A table's `content` is a Markdown table in GitHub's style (header, separator row, rows; `|` in a cell written `\|`); the separator row holds each column's alignment (`---` left, `:---:` centered, `---:` right; `:---` is read as left too).

## Database Errors

A database error is never an answer ([dberr.go](../internal/storage/dberr.go)):

- Functions that return an `error` pass it on.
- Functions that answer with a plain value (a bool, a count, a list) log it with the place it happened (`logDBErr`; message `Database query failed`, field `at`). Where they decide something they ask `dbFailed` and answer on the safe side: an account that cannot be checked counts as waiting for approval or confirmation, an address as taken, an administrator as the last one, a note as shared, the MCP switch as off.
- `sql.ErrNoRows` is an answer ("no such row"; `rowErr` turns it into `nil`). `context.Canceled` is a failure that is not logged: the request went away, nothing is wrong with the database.
- In list reads a row that cannot be scanned is logged and skipped; a read that breaks off (`rows.Err()`) is returned, or logged where there is no error to return.
- Statements nothing else depends on (`last_used_at`, cleaning up) run through `execLogged`. In the API, `logFailed` ([server.go](../internal/api/server.go)) does the same for steps the answer does not depend on (a mail on the side, removing a queue entry).

Dropped on purpose (`_ =`) are only best-effort seeding of sample data, `rows.Close()`, and decoding stored JSON columns.

## Migrations and Startup Cleanup

- Columns/tables/indexes are updated incrementally (`ALTER TABLE … ADD COLUMN`, errors ignored).
- Legacy tables are dropped: `spaces`, `space_members`, `space_team_shares`, `document_crdt_state`, `document_crdt_updates`, `document_blocks`, `doc_block_tags`, `revoked_tokens`.
- `users.username` is backfilled from the email prefix (baseline); migration 20 then sets it from the display name for every account (spaces and other characters become dots, a number is appended for duplicates). Migration 45 makes `idx_users_username` a UNIQUE index (`WHERE username != ''`), so two requests at the same moment cannot write the same name past the check in `uniqueUsername`/`SetUsername`. Before it, names held twice are resolved in one transaction: the oldest account (by `created_at`, then `rowid`, i.e. the one written first: ids are random) keeps the name, each later one gets the next number not held by anyone (`anna1`, `anna2` …), names not in lower case are lowered; every change is logged with old and new name. Afterwards a refused write becomes `ErrUsernameTaken` (`409 username_taken`), and creating an account tries the next free name (up to five times).
- Note synchronization (`migrateDocSync`): adds new columns to `blocks` (including `deleted_at`; existing tombstones are initialized with the migration timestamp) and `documents` (`head_seq`, `title_version`, `log_floor`), creates tables `doc_ops` and `doc_op_results`. Blocks in legacy flat format (using only `level`/`position`) are converted once into tree hierarchy.
- Default settings in `system_settings` (`INSERT OR IGNORE`): `sharing_mode=organizations`, `allow_registration=false`, `instance_name=MindSift`, SMTP empty.
- **Migrations:** [migrations.go](../internal/storage/migrations.go) executes numbered steps (3 "Base schema v0.4.1", 4 "Sessions", 5 "Media", 6 "Link previews", 7 "Notifications", 8 "Journal", 9 "Web-Push", 10 "Registration and invite links", 11 "Email confirmation", 12 "Marker for entries from AI agents", 13 "Origin of entries (API keys)", 14 "Clean up completed tasks", 15 "Voice input per person", 16 "Retention and trash for tasks", 17 "OAuth for MCP access", 18 "Folders in the trash", 19 "Language per person", 20 "Usernames from display names", 21 "Voice input language per person", 22 "Hidden values in notes", 23 "Several organizations per person", 24 "Public links to notes", 25 "Cleanup of used invites", 26 "Order of lists per person", 27 "Folder paths without spaces around slashes", 28 "Links to notes carry the note's id", 29 "Muted task lists and due alarms per person", 30 "Mentions in notes", 31 "Notification center", 32 "Reminders per task", 33 "New e-mail addresses wait for confirmation", 34 "Profile pictures only uploaded or emoji", 35 "Mail alarms go to the login address", 36 "Guided tour offered once to new accounts", 37 "Two-factor sign-in: authenticator app, recovery codes, trusted devices", 38 "Passkeys", 39 "Sign-in through an OpenID Connect provider", 40 "Accounts without an e-mail address", 41 "References from bullets to files and hidden values", 42 "Indexes for tasks from bullets and for deleted bullets", 43 "SMTP password encrypted with SECRETS_KEY", 44 "Note text stored only once", 45 "Usernames unique in the database", 46 "Hidden values copied with a bullet belong to its note") exactly once and records them in `schema_migrations` (`id`, `name`, `applied_at`); `PRAGMA user_version` reflects the highest applied migration number. Step 3 (`migrateBaseline`) sets up the baseline schema and migrates older databases to this level; columns are only created if missing. If a step fails, startup aborts with the error message instead of proceeding with a partially migrated schema. New schema changes are added as a new step at the end; old steps are never modified. Data is never deleted during startup; only demo mode resets the database.
- **Backup before migrations:** when steps are pending and the database already has tables (not a new or just reset one), `migrate` first writes a consistent copy (`VACUUM INTO`, gzipped, like the daily snapshot) to `$DATA_DIR/backups/system/pre-migration-<highest applied id>-YYYY-MM-DD-HHMMSS.db.gz` and logs its path. Without the copy (full disk: the uncompressed copy needs about the size of `mindsift.db` while it is written) nothing is migrated and the start stops with the reason. The newest three copies are kept, each for at most 90 days, the newest included (they hold accounts deleted since; the hourly cleanup in `api/done_cleanup.go` removes older ones by the time in the name, `Store.ExpirePreMigrationBackups`); they do not follow the daily backups' retention in days and are not listed in the administration (other name). Steps are not one transaction, so a failing step can leave the database half migrated: the file `backups/system/pre-migration-pending` names the copy from before the attempt until all steps went through, and while it is there that copy is kept beside the two newest, so a restart loop does not rotate it away. Databases without a file (`:memory:`) get no copy.
- **Newer database:** if `schema_migrations` holds an id above the highest step this binary knows, an older MindSift was started on a database a newer one has migrated. `migrate` then changes nothing and returns `storage.NewerDatabaseError` (both ids, the backup folder); the server logs it and does not start. Way back: run the newer image again, or stop, restore a pre-migration copy (unpack it over `mindsift.db`, remove `mindsift.db-wal`/`-shm`) and start the older image. Images up to v0.95.0 do not have this check and start silently on a newer database; accounts that signed in on the newer version cannot sign in there (password hashes with `sha256-bcrypt:`), so going back to them always means restoring the pre-migration copy ([operations.md](operations.md#rolling-back)).
- **Migration 44 "Note text stored only once"** ([note_storage.go](../internal/storage/note_storage.go), see [Note Text Stored Once](#note-text-stored-once)) converts existing notes: notes that only had `blocks_json` get their bullets, the log of every note is rewritten into references and deltas (one transaction per note; a bullet whose newest entry does not match its current text keeps its entries complete), the copies in `documents` are emptied, and `documents_fts` is built anew from the view. Afterwards, when that freed at least 8 MB and a quarter of the file, it runs `VACUUM` once and empties the WAL. `VACUUM` writes the compacted database twice for a moment, as a temporary copy in SQLite's temp directory (`SQLITE_TMPDIR`, `TMPDIR`, `/var/tmp`, `/tmp`) and once more into the WAL next to the database: on one file system it needs free space of up to about twice the size of the database, with the temp directory on another file system (in a container usually the image's `/tmp`) the size once in each place; with less (`statfs`, Linux only), it is skipped with a warning in the log. Skipped or failed, the freed space only stays in the file for reuse. Measured on a database with 17.8 MB of note text: 137 MB before, 24 MB after, in about 3 s. Whether notes are written in the new form is taken from the schema (the columns exist), not from the order of the steps, so a step that runs after 44 cannot write the old form into a converted log.
- **Only SQLite:** MindSift supports no other database; a `DATABASE_URL` starting with `postgres` is ignored with a warning (`config.Load`), so backup and check always apply to the SQLite file.

## Backup

The entire instance consists of the file `mindsift.db` (plus `-wal`/`-shm` during operation). Back up consistently using `sqlite3 mindsift.db ".backup 'backup.db'"` or by stopping the container and copying the `data/` directory. To restore a file, stop the server first and delete `mindsift.db-wal`/`-shm` before putting it in place ([operations.md](operations.md#restoring-a-whole-server)). Before schema migrations MindSift writes a copy of its own (see above); the daily snapshots are described in [architecture.md](architecture.md#background-job-backups). User export: `GET /api/v1/export` (JSON containing thoughts, notes, lists, task lists).

## Note Log Compaction <a id="verdichtung-des-notiz-logs"></a>

`Store.CompactDocs` runs on startup and every 6 hours thereafter (`startCompaction` in `internal/api/docsync.go`):

| Target | Retention | Effect |
|---|---|---|
| `doc_ops` of shared notes | 30 days | Older entries deleted; `documents.log_floor` tracks the compaction boundary |
| `doc_ops` of private notes | 7 days | Same as above |
| Tombstones in `blocks` | 30 days after `deleted_at` (found through the partial index `idx_blocks_deleted_at`, Migration 42) | Permanently purged; this is itself a `purge` log entry, applied by open editors without reloading. A tombstone is retained as long as a newer deleted child block references it. Log entries of the bullet still in the log get their texts written back into the payload first (they referred to the bullet). |
| `doc_op_results` | 90 days | Deleted |

A client whose `lastSeq` falls below `log_floor` (e.g. a device offline for weeks) receives `resync: true` from `/sync` and reloads the full snapshot; its pending unsent changes remain in the queue and are applied afterward. Text edits for a block that has since been permanently purged are appended as a new block at the end of the note; a new block whose parent was permanently purged is placed at the root level.

## Query Planner Statistics

`Store.Optimize` runs `PRAGMA optimize=0x10002` after the migrations at every start and at the end of every compaction run (every 6 hours): SQLite analyzes the tables whose size changed a lot since the last run and keeps the result in `sqlite_stat1`. Without these statistics the query planner guesses how selective an index is and can pick a poor plan (seen with `MediaOfUser`). `0x10002` checks all tables, not only those the pooled connection happened to query; SQLite caps the rows it reads per index (`analysis_limit`), so it stays quick on large databases.

In the same transaction it deletes the statistics of tables that had fewer than 1,000 rows (`minStatRows`) and of the shadow tables of the FTS5 indexes (`*_fts_data`, `*_fts_idx`, …). Statistics of a small table stop fitting once it grows, and the next run is hours away: on a new server the start analyzed `documents_fts_data` with 2 rows, the planner then scanned the whole index for every FTS5 merge (`DELETE … WHERE id>=? AND id<=?`), each note of an import took longer than the one before (1,000 notes: 16 s, 47 s, 84 s in three rounds), and the import held the write lock almost without a break, so other people's sign-ins failed with `SQLITE_BUSY` (re-test 2026-11-14, A1). Without statistics the planner assumes a large table and searches by index or rowid. A connection keeps the statistics it loaded when it opened (`ANALYZE sqlite_schema` does not reset the estimates of tables whose rows are gone), so `Optimize` closes the connection it analyzed with and the idle ones of the pool; one that was busy then is closed after at most an hour (`SetConnMaxLifetime`, not for in-memory test databases) and the next one loads the new statistics.
